Read-your-writes across Postgres replicas with an LSN token

This year I moved read traffic off a managed Postgres primary and onto self-hosted Postgres replicas on Kubernetes. Getting a copy of the data in sync was the straightforward part. The hard part was a bug every replica setup has on day one: you save something, the next request reads from a replica, and your change is not there yet.

This post is about the fix I shipped: a read-your-writes token based on the primary's WAL position. It also covers the details that only showed up because our data takes two hops to reach a replica. The idea is not new, and large teams route reads in similar ways. What I want to share is the execution.

The setup

  app writes --> managed Postgres primary
                        |
                        |  hop 1: native logical replication (decode + apply)
                        v
                 subscriber (self-hosted Postgres)
                        |
                        |  hop 2: physical streaming (WAL replay)
               +--------+--------+
               v                 v
           replica-1         replica-2     (behind a connection pooler)
               ^                 ^
               +---- read router <---- reads that carry a token

The managed primary feeds a self-hosted Postgres subscriber through native logical replication. The subscriber has two physical streaming replicas behind a connection pooler. Reads are routed by percentage, with a heartbeat-based staleness check and a circuit breaker.

The two hops are the important detail. A write has to be decoded and applied on the subscriber, and then the subscriber's own WAL has to be replayed on the replica. Either hop can lag.

Why the obvious fixes are not enough

The common shortcuts are to read from the primary for a few seconds after any write, or to pin a user to the primary for the rest of the session. Both work, and both throw away most of the reason you added replicas. They also guess: a fixed window is too long on a quiet night and too short during a lag spike.

I wanted the read to state exactly how fresh it needs to be, and the database to say whether it can serve that.

The token

After a write commits, the client asks the primary for its current WAL LSN, the log sequence number that marks a position in the write-ahead log. That value becomes the token. It means "show me data at least this fresh."

Web requests carry the token with them. Any read that carries it goes through a read router, which answers only from a replica that has applied that position.

Here is the catch with logical replication. The subscriber writes its own WAL with its own LSNs, so the primary's LSN means nothing if you compare it to the subscriber's position directly. What the subscriber does record is the replication origin's remote_lsn, the last primary position it has applied. That is the number to compare against the token.

The wait and the fallback

If the replica is behind the token, the router waits, at most one second, for replay to pass it. Usually that takes milliseconds. If no replica catches up in time, the router says so and the caller retries on the primary. The read gets slower, but it is never stale.

Generic pseudo code, not production code:

# after a write
commit(tx)
token = primary.scalar("select pg_current_wal_lsn()")
attach_to_session(token)

# router: serve a read that carries a token
def read_at_least(sql, token, max_wait=1.0):
    deadline = now() + max_wait
    while now() < deadline:
        applied = replica.scalar(
            "select remote_lsn from pg_replication_origin_status where external_id = $1", ORIGIN)
        if applied >= token:          # compare as pg_lsn, never as strings
            return replica.query(sql)
        sleep(0.005)
    raise Behind()

# client
try:
    rows = router.read_at_least(sql, session_token())
except Behind:
    rows = primary.query(sql)

The one second cap matters as much as the token. It bounds the worst case for a user, and it turns "replica is behind" into a clear, countable event instead of a slow request nobody can explain.

Extending it to workers

Web requests are only half the story. Background work has the same problem: a request writes a row, enqueues a job, and the job reads the row back from a replica before the row has arrived.

So the token travels in the job payload. Whoever enqueues a job after a write attaches the LSN, and the worker passes it to the same read path. I rolled that out across every runtime that reads from the replicas: background job runners, workers, the admin app and the job server.

The last step was making reads monotonic per scope, automatically. Within a scope, a later read should never see older data than an earlier one. Developers no longer have to remember to thread the token by hand.

The numbers

  • Median (p50) token wait, before tuning: about 110 ms
  • Median (p50) token wait, after wal_writer_delay=10ms: about 53 ms
  • Replica replay lag behind the subscriber, overnight: 1 to 5 ms
  • Lag guard alerts in that window: 0

One setting halved the median wait. wal_writer_delay controls how often the WAL writer wakes up to flush WAL that has not been flushed yet. Logical replication apply workers commit with synchronous_commit off by default, so applied changes can wait for the WAL writer before they reach a replica. At the default of 200 ms, that wait sat in the token path. At 10 ms, the median wait roughly halved.

What I would tell someone starting

  1. Name the freshness you need. A token beats a timer because it says exactly what the read requires.
  2. Know which LSN you are comparing. Across logical replication, the primary's position lives in the subscription origin, not in the subscriber's own WAL.
  3. Cap the wait and fall back. Slower is fine. Stale is a bug.
  4. Follow the write into background jobs. Read-after-write bugs do not stop at the web request.
  5. Look at the flush settings. A default that is fine for throughput can eat most of the latency budget for a token wait.
