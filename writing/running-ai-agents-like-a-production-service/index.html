Running AI coding agents like a production service

For most of 2026 my team used AI coding agents the way most teams do: one person, one session, watching it work. In September I started building something different. I call it Factory.

A teammate asks for a change in our team chat. A crew of agents plans it, writes it in an isolated copy of the repository, tests it, proves UI changes on a real iOS simulator, has a model from a different family judge the result blind, and comes back to the chat thread with a pull request and screenshots.

The agents turned out to be the easy part. What took the time was everything around them. That is the same list you need for any production service: a source of truth that survives crashes, leases so two workers never grab the same resource, health checks that run when nothing else does, failover when a dependency goes down, and gates that hold no matter what the caller says.

This post covers how Factory is put together, the incident that taught me the most, and what I measured.

The shape of it

   chat thread
        |
        v
 +----------------------- daemon (the only writer) ----------------------+
 |   append-only SQLite mailbox (WAL mode): every event is a letter      |
 +-----------------------------------------------------------------------+
        ^ pull           ^ pull              ^ pull             ^ pull
        |                |                   |                  |
   lead              executor            blind QA            chief
   one per thread    (fails over         (different model    (supervises
                     across vendors)     family)             the floor)
                         |
          own git worktree + leased iOS simulator
                         |
                         v
                   pull request  ------>  back to the chat thread

   watchdog: plain code, on its own clock, independent of the daemon

Letters, not pushes

Factory is one long-lived daemon. It is the only process that writes to an append-only SQLite database in WAL mode, which I call the mailbox. Every chat event, every message between agents and every decision is a letter appended to it. Nothing is updated in place.

Agents pull their work from the mailbox. The daemon never pushes into them. Each agent runs in a seat: a headless coding agent session that the daemon starts as a child process. If a seat crashes halfway through a task, nothing is lost. The letters are still there, and the replacement reads them and carries on.

With a single writer I never have to reason about write contention, and I get an exact, ordered history of what happened. When something goes wrong, I read the letters.

Seats and roles

Each seat has one job:

  • Lead. One seat per chat thread. It plans the work and talks to the person who asked.
  • Executor. Executor seats write the code, run the tests and walk the simulator.
  • Blind QA. A seat from a different model family judges the result blind.
  • Chief. Supervises the whole floor.

The split exists for the same reason a service does not approve its own deploys. The seat that built something is the worst judge of it, and two models from the same family are more likely to share a blind spot.

Isolation: worktrees and leased simulators

Every job gets its own git worktree, so two jobs never edit the same files. The worktree can sit on an instant APFS copy-on-write disk image of a fully installed monorepo, so a new job does not wait for a dependency install.

Jobs also get their own iOS simulator, on a lease. A lease is a claim with exactly one owner, the same pattern you would use for a distributed lock. A seat without a lease cannot drive a simulator. I cap local simulators and send overflow to a small cluster of office machines, chosen by one placement function.

Two changes made the cluster affordable. First, a slimmed simulator profile built for agent walks cut a simulator from about 300 processes to about 120, and from 4.3 GB to 1.6 GB of memory. Second, I moved to one agent per remote machine over one shared connection. Before, each remote seat cost 62.9 MB and two processes on the coordinating machine. Now it is about 3.3 MB per machine.

No single vendor

Executors fall back to a second vendor's model when quota runs low or the vendor has an outage. I treat a model provider like any other external dependency: decide the fallback before you need it, and switch automatically.

Rules live in code, not prompts

A prompt is a request. An agent working hard to finish a task will sometimes find a way around a request. So every rule that would cause an incident if broken is enforced by code that returns an error.

Gates that sit outside the agents' control refuse any simulator, push or approval action that a seat is not leased for, and every outgoing message is checked before it is posted. The release runner is deterministic code, and an AI seat appears only at the points that need judgment.

Watching the watcher

A watchdog runs on its own clock, always, independent of the daemon. There is no model in it. It is plain code, so it keeps working when the daemon or a model vendor is what broke.

The incident: 17 agents, 2.5 hours, no work

This fall, the model credentials Factory was using expired. The chief and 16 executors kept running turns, and each turn used zero tokens. Nothing failed loudly. It ran that way for about 2.5 hours before anyone noticed.

Looking back, every signal I had said the system was up. The processes were alive, the daemon was healthy and the mailbox kept moving. The one thing that was broken was the only thing that mattered: no work was getting done. A turn that consumes zero tokens is not a turn.

The fix was to make that failure visible. The watchdog now pages a person when agents keep taking turns that produce nothing. Time to detect went from about 2.5 hours, unseen, to under 30 minutes.

The general rule I took from it: check that a service produces output, not just that it is alive. It is the agent version of a web server that returns 200 with an empty body.

What I measured

  • Pull requests from Factory jobs, Sept 16 to Nov 5, 2026: 131 opened, 121 merged
  • Chat request to decision, p99: 31.6 s before, 0.45 s after
  • Same, during a slow-disk incident: 151 s before, 2.0 s after
  • Memory per agent simulator: 4.3 GB before, 1.6 GB after
  • Overhead per remote seat: 62.9 MB and 2 processes before, about 3.3 MB per machine after
  • Time to detect a credential failure: about 2.5 h before, under 30 min after

The latency win came from moving chat intake onto its own worker thread. During a 30 second daemon stall, each incoming event was still acknowledged in 0 to 2 ms.

One honest note. Since mid-September, most of the code I ship is written by agents that I designed, direct and review. What I am claiming is the system and the judgment built into it, not a typing rate. In a sample of 100 requests to Factory, 90 came from 11 teammates other than me.

Lessons learned

  1. The agents are the smallest part. Most of the work is the operations around them.
  2. One writer, append-only. A crash then costs a restart, not lost work, and the log explains every incident.
  3. Lease anything scarce. Simulators and push rights each have exactly one owner at a time.
  4. Enforce in code. If breaking a rule is an incident, a prompt is not enough.
  5. Separate the builder from the judge, and use a different model family for the judge.
  6. Keep the watchdog dumb. No model, its own clock, and no dependency on the thing it watches.
  7. Measure output, not liveness. Healthy processes doing nothing are the failure you will not see.
